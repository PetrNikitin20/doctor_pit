## Установка

1. Создать согласованную ВМ; открыть 80/443 для сайта и SSH только с адреса администратора. Не публиковать PostgreSQL, runner, Docker daemon. Включить защиту удаления диска и нужный режим резервирования. Установить Docker Engine/Compose из официального источника; для runner подготовить отдельный rootless Docker daemon либо отдельный узел.
2. Клонировать `PetrNikitin20/MKRmodel`. Создать `.env` из `.env.example`. Задать разные случайные PGPASSWORD и RUNNER_TOKEN (не менее 24 символов); пароль БД должен быть URL-безопасным. `APP_ORIGIN` должен совпадать с фактическим HTTPS origin.
3. Сначала собрать и проверить сервер без переключения действующего домена:

```sh
docker compose --env-file .env -f deploy/compose.yaml build app
docker compose --env-file .env -f deploy/compose.yaml up -d db
docker compose --env-file .env -f deploy/compose.yaml run --rm app node scripts/seed.mjs
docker compose --env-file .env -f deploy/compose.yaml up -d app
```

4. Передать закрытый SQL-снимок по SSH, проверить хеш, восстановить в пустую **новую** БД командой `psql -v ON_ERROR_STOP=1`. Снимок создаётся `node scripts/export-snapshot.mjs private/snapshot.sql`. Он не содержит активных сессий. Не смешивать этот способ с предварительным наполнением БД из п.3: для импорта снимка сначала применить только миграции, а затем снимок. Альтернатива — новый импорт закрытого payload через `scripts/import-private.mjs`, но он создаст новые временные пароли; старый файл доступов после этого неприменим.
5. Для исходного JSON: `docker compose ... run --rm -v "$PWD/private:/app/private" app node scripts/import-private.mjs /app/private/import.json`. Импортируемый каталог должен быть доступен UID 1000. Сохранить сгенерированный закрытый файл доступов. В рабочем контуре не создавать `demo-*` пользователей.
6. При подключении исполнителя:

```sh
# Выполнять в контексте того rootless daemon, чей socket передан runner:
docker build -f runner/Dockerfile.sandbox -t cop-python-sandbox:local .
# В .env: ROOTLESS_DOCKER_SOCKET, RUNNER_URL=http://runner:8081, RUNNER_TOKEN
docker compose --env-file .env -f deploy/compose.yaml --profile sandbox up -d --build runner app
```

7. Проверить runner на корректном/ошибочном коде, бесконечном цикле, попытке сетевого доступа, записи вне /tmp и чрезмерном выводе. Контейнер не должен иметь доступ к БД, ключам или домашнему каталогу. До этих проверок не объявлять выполнение кода готовым к эксплуатации.
8. Сделать `pg_dump`, восстановить в отдельную тестовую БД, сравнить количества и последние версии, проверить вход/смену пароля и роли. Запланировать ежедневные дампы (`deploy/backup.sh`) и копию в согласованном отдельном российском хранилище. Один файл на том же диске не защищает от потери ВМ. Настроить сигнализацию по сбоям и заполнению диска.
9. Только после проверки включить Caddy и сменить DNS `edu.petr-nikitin.ru`. Домен уже обслуживает УМНИК: перед переключением сохранить его данные и доступность прежних учебных сценариев, подготовить маршрут/архив старого приложения и план возврата DNS. `petr-nikitin.ru` — существующий личный сайт; не заменять его без сохранения содержимого. Сейчас ни один домен не изменён.
10. Проверить HTTPS и реальные логины из российской сети без VPN. Если проверка не прошла — вернуть прежнюю DNS-запись, не удаляя новую БД и резервную копию.

## Операционные ограничения

Не применять `docker compose down -v` к рабочему проекту: это уничтожит volumes. Для обновления сначала дамп, затем миграции/seed содержания, затем замена приложения. Изменения задач создают версии; старые попытки продолжают ссылаться на прежние условия и тесты.

Cloud Backup не заменяет согласованную проверку PostgreSQL восстановления. Ни RPO 24 ч, ни RTO 4 ч, ни SLA 99,9% пока не измерены. Исследовательская LLM на этой ВМ не размещается: 4 ГБ RAM рассчитаны на портал/БД и ограниченные учебные проверки.
